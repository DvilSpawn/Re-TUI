# Experimental community pane

Run `community` or its `irc` alias to open the opt-in Re-TUI community Activity. This is the integrated HTTPS launcher community, not an arbitrary-network IRC client. Nothing connects on launcher startup. Both F-Droid and Play Store use the same native username/password authentication at `https://irc.kokodoko.cloud/community`; no email, Google sign-in, social provider, Firebase, push, analytics or CAPTCHA dependency is added.

Use `/register` for public registration, or `/login` for an existing username. Authentication runs above and inside the **same composer**, not a modal: username → masked password → masked confirmation for registration, or username → masked password for login. Send/Enter advances each stage. Usernames use 3–24 ASCII letters, digits, `-` or `_`; passwords use 8–71 Unicode characters, matching the pinned backend's native password field limit. Validation and request errors appear in a bounded two-line guidance row. Invalid usernames stay at the username stage; password/confirmation or server failures clear secrets and restart at username. Touch **Cancel** or Back restores the conversation draft and forum title in the original context. `/cancel` also cancels at the username stage only; slash text in a password is always literal. Pause/recreation cancels authentication rather than retaining a password. Credential mode bypasses draft persistence and suggestions, disables view-state saving, autofill, prediction and personalized IME learning, and sets `FLAG_SECURE` on the Activity window until cancellation/completion, restoring any prior secure flag. Credentials remain short-lived in-memory request inputs, never commands, history, transcript or serialized conversation state. Registration is not sign-in: the app authenticates and validates a returned token before saving a session. A session token is saved encrypted; raw passwords are not saved. There is **no forgotten-password recovery**. Register a new username to continue: it is a separate identity; the old username is not reclaimed and ownership/history do not migrate automatically.

## Touch navigation

The floating pane reuses the help window's moving/resizing controller and the launcher's terminal font, frame, transparency and workspace colors. A vertical divider separates the approximately 20/80 channel rail and content area when channel labels and touch targets fit. Narrow windows or larger fonts collapse the rail; **Channels** still exposes every channel and its foreground mention count. Controls have a 48dp minimum target in source; final rendered bounds and keyboard/landscape behavior still require device acceptance.

**General** is a timeline with individually expiring messages. **Bugs**, **Help**, **Suggestions** and **Presets** are persistent forums; Suggestions uses the existing API key `features`. Touch **New thread**, enter a title and body, then Send. Tap a thread to read its root and replies, and use Back to return to the thread list. Titles allow 120 Unicode code points/480 UTF-8 bytes; bodies allow 500 code points/2000 bytes. Older/More pages are bounded, with explicit Latest navigation; ordinary polling does not replace an older thread-list window. Account-scoped thread/reply caches are rechecked against their own collections so moderation removals are reflected.

## Input

Plain text posts with Send or Enter; Shift+Enter inserts a newline. `exit` is a message, `/exit` leaves, and `//exit` posts `/exit`. Unknown slash commands are rejected locally. `settings; reboot` is literal text, never launcher or shell input. Received text is selectable but links do not automatically open or execute.

A horizontal launcher-style suggestion strip sits **below** the input. Signed-out empty or matching slash input offers `/register` and `/login`; signed-in slash input matches supported local commands. Tapping a command only inserts it—Send/Enter activates it. The same strip presents canonical `@` completion; signed-out mention input shows a login hint without a directory request. No suggestions or directory lookup run during authentication. Guidance/title, input and suggestion rows reserve the same height across General, forum lists, thread creation/detail and Mentions. Hidden composers are `INVISIBLE`, disabled, unfocused and excluded from accessibility, rather than removed from layout; returning restores the context draft. Font/host/IME changes may legitimately change the available viewport, but navigation with unchanged constraints does not change the dock budget.

Local commands: `/help`, `/refresh`, `/older`, `/login`, `/register`, `/logout`, `/exit`, `/report <full message ID>`, `/block <username>`, `/moderate <private text>`. The Menu exposes login/registration, message reporting, private moderation requests and logout without requiring slash commands. `/moderate` and the touch request dialog send only to the private moderator queue; an uncertain acknowledgement is not automatically retried because that endpoint has no idempotency UUID. Blocking is local and account-scoped; repeat to unblock. Reports display success only after server acceptance. Message limits: 500 Unicode code points and 2000 UTF-8 bytes.

## Handles, presence and mentions

Typing a token-boundary `@` at the caret opens completion after approximately 250ms. Up to 24 handle-fragment characters are sent; email-style tokens are ignored. The authenticated directory endpoint ranks case-insensitive exact, prefix, substring and subsequence matches; online breaks equal-relevance ties, and an empty fragment lists online users first. Tap a result to insert its canonical `@handle` at the caret, replacing only that token and preserving other text. Results and More are guarded by caret, context, account and foreground generations; obsolete requests are cancelled. Directory reads do not query the private members collection.

Online means a foreground community lease, not login or device connectivity. A separate client renews approximately every 30 seconds while visible, independently of posting; the server expires the lease after 90 seconds. Pause cancels work and never chains a request from a cancelled generation. The app relies on lease expiry rather than promising an immediate offline transition. There is no background service, FCM, push delivery, DM, attachment support or external IRC connection.

The server derives validated mentions from body text without changing message/thread/reply delivery payloads: at most ten distinct active recipients, excluding the author. **Mentions**, channel badges and bold highlighting of the current recipient are foreground in-app indicators only. The recipient-only list stores bounded routing metadata and account-scoped read IDs, not duplicate bodies. General metadata expires at its source's 24-hour cutoff; forum metadata/read markers persist within a 200-entry bound. Returning to a seen page does not immediately resurrect its unread marker; markers eventually evicted from the bound can reappear unread. Tapping a source fetches that exact record (and its parent thread where appropriate), not an expanded unrestricted history; expired/deleted sources disappear gracefully.

The HTTPS base is `https://irc.kokodoko.cloud/community`:

- `GET /api/community/users?q=fragment&page=1&perPage=20` → `{page,perPage,hasMore,items:[{id,handle,online}]}`.
- `POST /api/community/presence` with `{active:true}` → `{online,expires_at}` (server also accepts `{active:false}`).
- `GET /api/community/mentions?page=1&perPage=50` → `{page,perPage,hasMore,items:[{id,kind,source_id,thread_id,channel,author_handle,created,expires_at}]}`, where kind is `message`, `thread` or `thread_reply`. Maximum perPage is 50 and page is 1000; pages count currently accessible items. The backend checks at most 1,000 recipient metadata rows plus one metadata-only exhaustion probe per request. If it cannot establish a complete page/end within that ceiling, it returns HTTP **503** `{"status":503,"message":"Mention scan limit exceeded.","data":{}}`, not partial success or `hasMore=false`. Treat it as a failed GET, retain only valid stale cache without marking absent mentions read or advancing pages, and back off before retrying the same page. Do not immediately retry or repeatedly walk pages to bypass the ceiling; persistent failures require backend/operator review. Valid deep page parameters do not guarantee a successful response.
- Native `threads` posts use `{author,channel,title,body,client_id}`; `thread_replies` posts use `{author,thread,body,client_id}`. Explicit collection filters and `(created,id)` cursors isolate channels/parents. Source reads use their exact native record path.
- Private `moderator_requests` posts use `{reporter,kind:"moderate",body}`, without a UUID or blind retry.

## Storage and delivery

The local cache holds at most 200 general-message bodies, 200 thread summaries and 200 reply bodies, plus the selected root. Per-context editable drafts and immutable pending forum payloads are separate from general delivery state; thread-list and reply cursors are independent. Encrypted state is capped at 4,000,000 bytes. Loading `/older` moves this bounded window toward earlier history; ordinary timer polls recheck it without forcing a scroll. Newer arrivals outside that window are announced in the unread header using at most 50 body-free ID/author metadata entries and a separate newest-observed cursor. `/refresh` explicitly returns to the latest window and scrolls to its newest messages; a successful own post immediately fetches the latest peer page, retains its canonical acknowledgement and is marked read. If that follow-up fetch fails, delivery remains successful and the status separately labels the feed stale; the post is not resent. The history/latest mode and arrival observations survive recreation. Account token, cache, local blocks, read markers and draft are encrypted with an AndroidKeyStore AES-GCM key in `noBackupFilesDir/community/state.bin`, outside launcher preset/personal exports and Android backup. Logging out clears all account state; switching accounts does not share cache or draft. Leaving an unsent draft offers Keep, Discard or Cancel. Nothing posts automatically on restoration.

A post gets a persisted UUID and immutable body before sending, separately from the editable draft. A retained attempt is treated as potentially delivered, including after network failure, any HTTP 5xx response, or lifecycle cancellation. Submitting again looks up that original author/UUID/body **before** retrying; a failed lookup keeps the identity and sends no retry POST. A successful empty lookup allows a same-UUID retry, but a later rejection still cannot prove the original attempt never committed. Only a first-attempt validation HTTP 400 (after successful empty reconciliation) or HTTP 429 releases the attempt marker without discarding the draft. A matching canonical record completes delivery; neither a duplicate HTTP 400 nor a gateway failure alone proves delivery or rejection. A newer editable draft is never sent under the original UUID, and completion preserves it across recreation. Submit again after completion to send the newer draft. HTTP 401/403 clears private account state under the logout policy, without claiming that a potentially committed post was retracted. Discarding or logging out does not retract a post that may already have reached the server.

Polling runs only while the Activity is visible, normally every 15 seconds, without overlapping requests. Pause cancels requests and polling, permanently invalidating that operation before any later chained request or checked-ID chunk. Reentry starts a fresh operation without reviving the cancelled one; a cancelled post keeps its pending UUID/body for manual reconciliation. Errors retain only unexpired stale cached history, with backoff. A separate foreground callback on the existing UI handler expires cached/rendered bodies and arrival metadata at their server `created` timestamp plus 24 hours, even while refresh is failing, backed off or busy. It stops on pause and rechecks on resume; it is not a background service. Exact age >=24 hours, invalid timestamps and future-dated records are excluded. `updated` never extends retention. Expiry does not release an uncertain post UUID/body or erase an editable draft. Older body-free arrival metadata without a creation timestamp is discarded rather than kept indefinitely. Refresh rechecks bounded cached IDs so moderation deletions are reflected without treating absence from the latest page as deletion. Expired/revoked sessions clear private account state.

## Foreground request budget

At a full 200-record cache, a General or thread-list refresh costs one page plus four checked-ID chunks (50 IDs each): up to 20 GETs/minute at the normal 15-second cadence. Reply detail adds a parent lookup: up to 24 GETs/minute. A mention refresh normally needs one GET, but can fetch four pages and revalidate up to 200 cached omissions across three source collections. Chunk rounding can require six additional GETs, giving a bounded maximum of ten GETs per mention refresh, or 20 GETs/minute at its 30-second cadence. Combined polling ceilings are therefore 40 GETs/minute for General/thread lists or 44 for reply detail, plus two independently limited presence POSTs, before manual navigation, delivery reconciliation or autocomplete. Typing with pauses at the 250ms debounce boundary can add up to approximately 240 directory GETs/minute; this is not a reserved quota. Shared-IP read throttling can still limit busy users; 429 responses defer presence/mention renewals, and autocomplete is retried only after another user action. Mention pagination or scan-limit errors preserve the previously validated window rather than declaring unseen pages empty. Read and presence buckets must remain separate from message-post limits.

## Pilot limitations

The Android surface now includes General, persistent forums, foreground presence and recipient-only in-app mention indicators. It does not include private messages, attachments, recipient read receipts, push delivery, an external IRC connection or a background service. Messages are server-readable, **not end-to-end encrypted**. The backend v2 contract expires each general message individually at age **>=24 hours** from immutable server creation in UTC (not midnight or last edit); API reads hide expired/future-dated messages immediately, with physical purge normally every minute. Accounts persist. Accepted reports retain private snapshots of reported text/author and reasons for **six calendar months** after report creation in UTC, with end-of-month clamping, not 180 days; deleting the source message/account does not remove that evidence. Active assigned moderators and loopback administrators can read it.

The v3 endpoints and Help migration are required for directory/presence/mentions and the `help` forum. Android browsing, thread/reply composition and private `/moderate` requests are implemented; moderator queue reading/resolution is not. `/report` succeeds only on server acceptance and cannot report an expired source. Private reports and moderator requests retain server-readable evidence for six calendar months, not public posts.

Local expiry relies on the device wall clock and runs when state is restored, merged, saved or rendered, and while the Activity is visible. An unopened/paused app cannot rewrite its encrypted on-disk cache at the cutoff; it prunes on next access/save. Drafts and immutable uncertain-delivery bodies are separate user-controlled state, not timed chat history. This is not forensic secure erasure of storage, memory, WAL/free pages or provider snapshots. Scheduled whole-database server archives are disabled because they would preserve expired text, but unresolved legacy archives/rollback copies remain retention exceptions; no offsite backup is configured and persistent identities/threads have single-VPS loss risk. See [the backend contract](../server/community/README.md) for policy and operational limits. PocketBase is pre-1.0: this optional experimental feature and its storage/API may change.

Release gates include deployed public-registration rules/rate limits, validated TLS and collection authorization, authenticated two-user live integration, and final release-flavor/device regression checks. Host unit tests use production state/input/client code with real loopback HTTP fixtures. Source-wiring guards are not rendered-UI evidence. The new `CommunityPaneIntegrationTest` and concurrent socket fixture are disposable-emulator-only: they clear fixture account storage, launch/recreate/background the Activity and must never run on a data-bearing phone. They are compiled but not executed for this change; neither those fixtures nor host tests establish production availability, rendered visual parity or physical-device compatibility.

`CommunityLiveIntegrationTest` is skipped unless instrumentation receives `-e liveCommunity true`, and is restricted to disposable emulators. It uses the fixed production HTTPS endpoint with ordinary certificate validation and generates credentials only in memory. It emits only its unique temporary usernames/member IDs for operator cleanup; after any run, remove only those exact fixtures and verify their related messages/reports are gone. It respects rate-limit delays with bounded foreground waits.
